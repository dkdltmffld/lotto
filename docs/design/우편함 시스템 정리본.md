# 우편함 시스템 정리본

> ✅ **기획 초안 → 1차 구현 완료(2026-06-11).** 플레이 테스트 중 재화 지급 필요성이 확인되어 작성한다. 우편함은 보상·보정·이벤트 지급을 유저에게 전달하는 공용 통로다.
>
> 구현 파일: `scripts/mailbox.gd`(`Mailbox` — 카탈로그 상수 + 순수 판정 로직), `scripts/mailbox_panel.gd`(`panel_overlay_base` 상속 전체화면 오버레이), `scripts/red_dot.gd`(`RedDot` 공용 배지), `backend_service.gd` mail API(`get_mail_claimed`/`is_mail_claimed`/`mark_mail_claimed`/`gc_mail_claimed`), `tools/tests/test_mailbox.gd`.
>
> 상위: [[게임 컨셉 정리본]], [[백엔드 시스템 정리본]], [[리텐션 시스템 정리본]], [[BM 시스템 정리본]].

## 1. 목적

우편함은 게임 내 재화를 직접 지급하기 위한 안전한 통로다.

필요한 이유:
- 플레이 테스트 중 골드/다이아/유물 가루 지급이 필요해졌다.
- 출석·업적·이벤트·보상형 광고·점검 보상 등 여러 시스템이 보상 지급 UI를 공유할 수 있다.
- 보상을 즉시 인벤토리에 꽂는 것보다, 유저가 "받기"를 누르게 하면 지급 내역과 감각이 명확하다.

우편함은 경제 시스템이 아니라 **보상 전달 시스템**이다.

## 2. 기본 원칙

1. **보상은 수령식으로 지급한다.**
   - 우편이 도착해도 재화는 즉시 증가하지 않는다.
   - 유저가 `받기` 또는 `모두 받기`를 눌렀을 때 재화가 지급된다.

2. **우편은 지급 내역을 설명한다.**
   - 왜 받는 보상인지 알 수 있어야 한다.
   - 제목, 본문, 보상 목록, 만료 여부를 표시한다.

3. **수령은 이산 이벤트다.**
   - 보상·`claimed`를 메모리에 반영한 뒤 `BackendService.flush()`로 즉시 영속화한다(모두받기는 1회 — 수령 시퀀스는 §6-0).
   - 중복 수령을 막기 위해 수령 상태(`mail_claimed`)를 저장한다.

4. **우편함은 허용된 재화 키만 다룬다(화이트리스트).**
   - 1차 허용 = 골드·다이아·유물 가루 `{gold, dia, dust}`. 그 외 키는 차단(§5).
   - 추후 아이템/유물/장비 직접 지급은 별도 확장으로 본다.

5. **동적 운영 우편과 로컬 우편을 구분한다.**
   - 현재 백엔드 구조만으로는 서버에서 임의 유저에게 실시간 우편을 밀어 넣는 기능이 없다.
   - 1차는 클라이언트 정의 우편/보상 수령 통로로 시작하고, 동적 운영 우편은 별도 백엔드 또는 kplay 지원 여부 확인 후 확장한다.
   - (kplay storage는 클라이언트 저장 동기화에 가까운 **pull 모델** — 서버가 유저에게 푸시하는 채널이 없다. 진단 확정.)

6. **⚠️ mail id는 영구 유일 — 한 번 쓴 id는 재사용 금지.** (가장 중요한 규칙)
   - 중복 수령 방지는 `mail_claimed = {id: true}` 도장 하나로만 판정한다.
   - 한 번 발행한 id는 **보상이 달라도** 재사용하지 않는다. 재지급이 필요하면 **새 id**를 발급한다.
   - 컨벤션: `mail_<YYYYMMDD>_<slug>` (예: `mail_20260611_test_reward`).
   - **이 규칙이 §7 claimed GC의 안전 전제다** — 둘은 한 세트로 본다.

## 3. 사용처

| 사용처 | 우선순위 | 설명 |
|---|---|---|
| 플레이 테스트 보상 | 높음 | 테스트 중 재화 부족 보정, 진행 확인용 지급 |
| 점검/업데이트 보상 | 중간 | 배포 후 보정·사과 보상 |
| 이벤트 보상 | 중간 | 기간 한정 접속 보상, 쿠폰성 지급 |
| 광고 보상 | 낮음 | 향후 **광고로 주는 재화성 보상**이 생길 때만. ⚠️ BM의 주 광고 보상은 *자동긁기 시간제 버프(재화 아님)*라 1차 우편 대상 아님([[BM 시스템 정리본]] §2) |
| BM 패키지 | 낮음 | 구매 상품 배송 통로 후보(1차 제외) |

1차 목표는 **테스트/운영 보상 + 재화 지급 UI**다.

> **리텐션/퀘스트와의 경계 (확정): 우편함은 리텐션·퀘스트와 독립.** 출석·복귀 보상은 [[리텐션 시스템 정리본]], 목표/진행도 기반 보상은 [[퀘스트 시스템 정리본]]이 맡는다 — 우편함을 거치지 않는다. 우편함은 **운영/테스트/이벤트 일회성 보상**만 맡는다. (각 시스템이 "수령식 claim + 뱃지 + flush 1회" 패턴을 공유할 수 있지만, 1차는 통합하지 않고 독립으로 둔다.)

## 4. 우편 데이터

우편 1개는 아래 정보를 가진다.

```
{
  id: "mail_20260611_test_reward",
  title: "테스트 보상",
  body: "플레이 테스트 진행을 위해 보상을 지급합니다.",
  rewards: [
    { currency: "gold", amount: 100000 },
    { currency: "dia", amount: 5000 }
    // ⚠️ 유물 가루(dust) 보상은 2026-06-17 제거 — 가루는 보스/상점(재화)/중복환급/퀘스트로만.
    //    (화이트리스트엔 dust 잔존하나 우편 카탈로그가 안 씀)
  ],
  created_at: 1781100000,   // (개념 필드 — 1차 코드 카탈로그는 미사용)
  expires_at: 0,
  source: "test",
  claimed: false
}
```

필드:
| 필드 | 의미 |
|---|---|
| `id` | 우편 고유 id. 중복 수령 방지 기준 |
| `title` | 목록/상세 제목 |
| `body` | 지급 이유 설명 |
| `rewards` | 보상 목록 |
| `created_at` | 생성 시각 |
| `expires_at` | 만료 시각. 0 또는 누락이면 만료 없음 |
| `source` | test/event/compensation/system 등 (⚠️ retention 제외 — §3대로 리텐션은 우편함 비대상) |
| `claimed` | 수령 여부 |

## 5. 보상 타입

1차 지원:

| 타입 | 키 |
|---|---|
| 골드 | `gold` |
| 다이아 | `dia` |
| 유물 가루 | `dust` |

> **책임 경계 (중요): 우편함은 "어떤 재화 키(gold/dia/dust)를 전달할 수 있는가"(화이트리스트)만 소유한다.** 각 우편의 **지급량·대상·상한은 우편함의 책임이 아니라 그 우편을 발행하는 주체**(테스트/이벤트/운영)가 정한다(§1의 "전달 시스템" 정의 정합 — 우편함은 경제 결정 주체가 아니다).
> 발행 주체가 지급량을 정할 때 참고할 게임 전체 재화 역할 기준은 [[재화 정책 초안]]에 있다(우편함이 그 문서의 하위라는 뜻이 아니라, 발행자가 들여다볼 외부 횡단 문서). 우편함 문서는 특정 재화의 정책 세부를 담지 않는다.

**지급 경로 = 통화 일반화 통로 하나로.**
```
BackendService.add_currency(reward.currency, reward.amount)
```
- `reward.currency`(§4의 통화 키)를 그대로 `add_currency(name, amount)`에 라우팅한다. `add_gold`/`add_dia`/`add_dust`는 이 위의 얇은 별칭이므로 **우편 지급에서 별칭 분기(`match`)를 쓰지 않는다** — 새 재화가 생겨도 `_migrate` 기본값만 추가하면 우편 지급이 자동 지원된다.
- `amount`는 **양수만** 허용한다(`add_currency`가 음수를 무시·경고).
- ⚠️ **미지원/오타 currency 키 차단은 우편함이 직접 한다.** `BackendService.add_currency`는 키를 검증하지 않고 임의 키를 그대로 세이브에 박는다(예: `"diia"` 오타도 새 키로 저장됨 — 음수만 거름). 따라서 **우편함이 지급 직전 `reward.currency`를 허용 재화 집합 `{gold, dia, dust}`(= `CUR_GOLD/CUR_DIA/CUR_DUST`)와 대조해, 없으면 그 보상만 스킵 + `push_warning`** 하고 나머지는 정상 지급한다(수령 시퀀스 §6-0 안에서 스킵). 발행 시점(§4 카탈로그 정의)에도 같은 검증을 권장.
  - (BackendService에 허용 재화 검증을 넣는 대안은 전 호출부[전투 골드 가산 등] 영향이라 별도 결정 — 1차는 우편함 측 검증만 채택.)

추후 확장 후보:
| 타입 | 예시 | 비고 |
|---|---|---|
| 장비 | 특정 장비 uid 생성 | 장비 인스턴스 모델과 연결 필요 |
| 유물 | 특정 effect/grade 지급 | `BackendService.acquire_relic` 사용 가능 |
| 광고 버프 | 자동 긁기 속도 버프 | 시간제 버프 시스템 필요 |
| 이벤트 티켓 | 유물 복권 티켓 등 | 별도 재화/아이템 정의 필요 |

초기에는 재화 3종만 지원한다. 장비/유물 직접 지급은 우편함 구조가 안정된 뒤 확장한다.

## 6. 수령 정책

### 6-0. 수령 시퀀스 — 메모리 일괄 반영 (단일·모두받기 공통, 가장 중요)

⚠️ **보상 가산과 `claimed` 표시는 모두 메모리(`_data`)에 먼저 반영하고, `flush()`는 마지막에 1회만 한다.**

```
(메모리) 보상 add_currency × N + mail_claimed[id]=true × N  →  flush() 1회  →  Events.currency_changed.emit()  →  결과 토스트
```

- 보상과 claimed를 **같은 `_data` dict에 먼저 반영**하므로 **메모리 수준에서 부분 반영이 안 생긴다**(둘이 한 dict). 단 **flush(영속화)까지의 완전한 DB 트랜잭션은 아니다** — `save_all`은 localStorage(소스 오브 트루스) 성공만 반환하고 kplay 클라우드 `storage-set`은 fire-and-forget이라 localStorage와 클라우드가 한 트랜잭션으로 커밋되지 않는다(클라우드 일관성은 비동기 재동기 `storage-resynced`/8초 타임아웃 경로로 보정).
- **건별 flush 금지.** 보상 지급과 claimed 저장 사이에 크래시/종료가 끼면 이중 지급(claimed 누락) 또는 부분 지급 구멍이 난다. 메모리 일괄 반영이 이 위험을 줄인다.
- flush가 실패해도(웹 quota/프라이빗 모드) `_dirty`가 유지돼 다음 autosave가 재시도하며, 메모리엔 이미 `claimed=true`라 재지급되지 않는다(`BackendService._persist_now`의 `_dirty = not ok` 패턴).
- **수령 멱등성**: 수령 직전 `mail_claimed[id]`가 이미 true면 보상 가산을 스킵한다(이중 지급 구조적 차단).
- **HUD 갱신**: 재화 반영 후 반드시 `Events.currency_changed.emit()` — 안 하면 좌상단 골드/다이아가 다음 `_refresh_hud`까지 옛 값으로 남는다(shop_panel·relic_panel과 동일 패턴, 값은 안 싣고 "변했다"만 통지).
- **결과 토스트**: 우편함이 재화별 합산을 **문자열로 직접 조립**해 `NotificationManager.reward(text)`(여러 줄 가능)로 넘긴다 — NotificationManager는 합산/포맷을 해주지 않는다. (여러 보상 카드 그리드 팝업을 원하면 shop_panel 결과 모달 패턴을 별도로 만든다.)

### 6-1. 단일 수령

흐름:

```
우편 선택 → 받기 → (6-0 수령 시퀀스) → 결과 토스트
```

조건:
- 이미 수령한 우편(claimed)은 다시 받을 수 없다.
- 만료된 우편은 받을 수 없다.
- **1차는 빈 보상 우편을 만들지 않는다**(카탈로그에 보상 없는 우편 미발행) — "읽음 처리만" 상태는 2차로 미룬다(§8이 읽음/안읽음 상태를 1차 제외하므로 정합).

### 6-2. 모두 받기

흐름:

```
받을 수 있는 우편 필터링 → 보상 합산(메모리) → claimed 일괄 표시(메모리) → flush 1회 → emit → 합산 토스트
```

원칙:
- `모두 받기`도 §6-0 수령 시퀀스를 따른다 — 모든 보상·claimed를 메모리에 반영한 뒤 flush 1회.
- 지급 결과는 재화별 합산 문자열로 보여준다(우편함이 조립).
- 1차는 재화 지급만 지원해 실패 표면을 최소화한다(`add_currency`는 실패 반환이 없어 사실상 지급 자체는 실패하지 않음 — 진짜 위험은 위 §6-0의 flush 타이밍이고 그것을 메모리 일괄 반영으로 줄인다).

### 6-3. 만료

만료 정책:
- `expires_at`이 있고 현재 시간이 지났으면 수령 불가.
- 만료 우편은 목록에서 흐리게 보이거나 자동 숨김 처리한다.
- 1차는 자동 삭제보다 "만료됨" 표시가 안전하다(claimed 정리는 §7 GC가 별도로 다룸).

시간 기준:
- **1차는 우편함 내부 시간 추상화 헬퍼**(`Mailbox.now()`, 로컬 폴백 = `Time.get_unix_time_from_system()`)로 만료를 판정한다. 우편함이 `Time`을 산발 호출하지 않고 이 헬퍼 **한 지점**만 거치게 해, 추후 리텐션 [[리텐션 시스템 정리본]] `DayUtil` 또는 서버 시간이 준비되면 그 한 지점만 교체/통합한다. (⚠️ `DayUtil`은 아직 미구현이라 우편함 1차를 리텐션 선행 작업에 묶지 않는다 — "시간 소스를 한 곳으로 추상화" 정신은 유지.)
- `created_at`/`expires_at`는 Unix초(백엔드 `last_seen`과 동일 단위).
- 1차 만료 판정 = 로컬 시계 폴백. 시계 조작으로 만료 우회·재수령이 가능하나 **랭킹 비활성이라 테스트/운영 보상엔 무해**. 정적 우편은 만료를 미사용하거나 `created_at` 기반 상대 만료로 어뷰징 표면을 줄이는 방향도 검토.

## 7. 저장 구조

저장 키 후보:

```
mail_claimed: { mail_id: true }
mail_deleted: { mail_id: true }   # 선택 사항
mail_local: [ ... ]               # 로컬 생성 우편을 저장할 경우
```

정책:
- 정적/클라이언트 정의 우편은 코드 상수(1차)에 있고(추후 데이터화 가능, §7 1차 권장), 세이브에는 수령 여부만 저장한다.
- 동적으로 받은 우편은 `mail_local` 같은 배열에 저장해야 한다.
- kplay 저장 한도(value 10KB)를 고려해 우편 본문 전체를 무제한 저장하지 않는다.

1차 권장:
- 우편 카탈로그는 **코드 상수 딕셔너리로 시작**한다(가장 단순·10KB 안전). 데이터화가 필요해지면 `data/src/mail.yaml → build_data.gd(FILES+_validate) → data/*.json → GameData.table("mail")` 경로를 쓴다. ⚠️ YAML 서브셋 파서가 **블록 리스트(`- item`)를 미지원**하므로 `rewards`는 인라인(`[...]`)이나 맵 구조로 설계한다.
- 세이브에는 `mail_claimed`만 저장한다.
- **`mail_claimed`는 `_migrate`에 등록한다**: `_ensure_container(d, "mail_claimed", {})` 한 줄(손상/구버전 세이브에서 타입 어긋남 방어). `set_value`만 쓰면 `_migrate`를 안 거쳐 방어가 안 된다. (`mail_deleted`/`mail_local`을 쓰면 동일 처리.)

### 7-1. mail id 규칙 + claimed GC (한 세트)

⚠️ **mail id는 영구 유일 — 한 번 발행한 id는 보상이 달라도 재사용 금지**(§2-6 재확인). 재지급이 필요하면 새 id. 컨벤션 `mail_<YYYYMMDD>_<slug>`.

**claimed 누적 완화 = 카탈로그 제거 GC (확정).**
- 문제: `mail_claimed` 도장은 수령할 때마다 영구 누적된다(우편 본문이 아니라 **받았음 기록**이 쌓임). 단일 세이브 키(gold/장비/유물과 공유, gzip 압축돼도)를 장기적으로 압박.
- GC 규칙: **카탈로그에서 제거됨** — 카탈로그에 더 이상 없는 id의 claimed 도장을 정리한다.
  - 카탈로그에 아직 살아있는 우편은(만료만 됐어도) claimed를 **유지**한다 — 재수령 방지.
  - 운영자가 우편을 카탈로그에서 빼는 행위 = "이 우편 다시 안 쓴다" 선언 → 도장 지워도 안전.
- **⚠️ '만료됨' 조건은 GC 기준에서 뺀다.** `claimed` 도장은 id만 보유(§7)하고 `expires_at`는 카탈로그 엔트리에만 있어, 카탈로그에서 제거된 id는 만료 여부를 판정할 정보가 없다(두 조건이 상호배타 — "만료됨 AND 카탈로그 제거됨"은 구조적으로 평가 불가능했다). 그리고 아래 id 재사용 금지가 재수령을 원천 차단하므로 '만료됨' 조건은 **불필요**하다. 만료(`expires_at`)는 화면 표시·수령 가드(§6-3)용일 뿐 GC 기준이 아니다.
- **GC 안전은 "id 재사용 금지"(§2-6)에 100% 의존한다.** 도장을 지운 뒤 같은 id가 카탈로그에 다시 나타나면 재수령(이중 지급)되기 때문. 그래서 두 규칙은 한 세트로 본다.
- **구현: GC는 두 곳에 있다(판정 기준 동일 — "id ∈ 카탈로그면 유지").** `Mailbox.gc_claimed`(순수 테스트용 미러 — autoload 무참조라 헤드리스 `--script` 테스트 가능, `tools/tests/test_mailbox.gd` 전용) / `BackendService.gc_mail_claimed`(프로덕션 in-place, 시작 시 1회). **GC 기준을 바꾸면 두 곳을 함께 수정**한다.
- (대안 기각: `mail_claimed_meta:{id:expires_at}`로 만료를 같이 저장하면 도장 페이로드가 커져 10KB 압박이 악화되고, `tombstone` 목록으로 제거 id를 보관하면 또 다른 누적 키가 생겨 자기모순 — 둘 다 "누적 완화" 목적과 충돌해 채택 안 함.)

### 9-1. 공용 red dot 컴포넌트 (확정)

빨간 점은 **재사용 가능한 공용 dot 컴포넌트**로 만든다(우편함·리텐션 등이 공유).

- 사유: `NotificationManager`는 떴다 사라지는 토스트 전용, `UIManager`는 열고 닫는 표면 전용 — 상시 배지의 집이 없다. 리텐션도 같은 빨간 점이 필요(`RetentionStatus.has_claimable()`)하므로 한 컴포넌트로 통일한다.
- 형태: 버튼/아이콘 우상단에 붙는 작은 Control(점 + 선택적 카운트). 소유자가 `set_active(on)`로만 토글(`RedDot` API).
- 판정 소유: 우편함은 `Mailbox.has_claimable()`(받을 수 있는 미수령·미만료 우편 존재)을 폴링/구독해 dot을 토글. 값 계산은 우편함이, 표시는 공용 dot이.
- ⚠️ NotificationManager에 넣지 않는다(토스트 전용).

## 10. 백엔드 / 운영 제약

현재 구조:
- `BackendService`는 저장/로그인/재화 반영을 담당한다.
- kplay storage는 클라이언트 저장 동기화에 가깝다.
- 현재 설계만으로는 운영자가 서버에서 특정 유저에게 우편을 직접 발송하는 구조가 아니다.

따라서 우편함은 단계적으로 본다.

| 단계 | 방식 | 설명 |
|---|---|---|
| 1차 | 클라이언트 정적 우편 | 코드 상수에 정의된 우편 + 수령 여부 저장 |
| 2차 | 버전/이벤트 우편 | 앱 버전·날짜·이벤트 조건에 따라 생성 |
| 3차 | 원격 우편 | 자체 백엔드 또는 kplay 지원 확인 후 운영 발송 |

운영 우편이 필요해지면 확인할 것:
- 서버 시간
- 원격 우편 목록 수신 방식
- 유저별 지급/전체 지급 구분
- 중복 수령 방지 id
- kplay 저장 한도와 동기화 방식

### 10-1. 슬롯 격리 (게스트)

`mail_claimed`는 단일 세이브 dict에 들어가고, 슬롯이 분리돼 있다([[백엔드 시스템 정리본]]) — 인증 계정은 클라우드 동기, 게스트는 로컬 전용(기기·브라우저별 IndexedDB 격리).

- 따라서 **게스트는 기기/브라우저마다 정적 우편을 재수령할 수 있다**(claimed가 그 기기에만 남으므로).
- **결정(확정): 일회성 보상은 게스트가 받아도 무방.** 어차피 일회성 지급이고, 게스트 다중 기기 재수령은 운영상 무시 가능. (민감한 대량 보상이 생기면 그때 인증 계정 한정으로 재검토.)

## 11. 결정 현황

### 확정 (2026-06-11 검토 → 1차 구현으로 실현)
아래 결정들은 코드로 실현됐다.
- **책임 경계**: 우편함 = 전달 통로(재화 키 화이트리스트 + 수령 메커니즘). 지급량/대상/상한 = 발행 주체(§5). → `Mailbox`(카탈로그 + 화이트리스트만 소유)/`mailbox_panel`(지급 수행) 분리로 실현.
- 우편함 = 리텐션과 **독립**(§3).
- 빨간 점 = **공용 dot 컴포넌트**(§9-1). → `RedDot`(`class_name RedDot`, `set_active(on)`).
- 시간 소스 = **우편함 내부 시간 추상화(로컬 폴백)**, 추후 리텐션 `DayUtil`/서버 시간과 통합(§6-3). → `Mailbox.now()`(로컬 `Time` 폴백) 한 지점.
- 게스트 일회성 보상 = **받게 둠**(§10-1).
- claimed 누적 = **카탈로그 제거 GC + id 영구 유일**(§7-1). → `Mailbox.gc_claimed`(순수 미러)/`BackendService.gc_mail_claimed`(프로덕션).
- 지급 = `add_currency` 일반화(미지원 키는 우편함 whitelist로 스킵) / 메모리 일괄 반영 시퀀스 / `Events.emit` / `_migrate` 등록 (§5·§6-0·§7). → 화이트리스트 = `Mailbox.ALLOWED_CURRENCIES`/`is_currency_allowed`.
- 카탈로그 = **코드 상수로 1차 시작**(§7). → `Mailbox.CATALOG`(더미 우편 3종).
- UI = **상단 HUD + `register_overlay`**(§9). → `mailbox_panel`(`panel_overlay_base` 상속, `UIManager.open_overlay("mailbox")`).

### 아직 결정하지 않음 (구현/밸런스 시)
- 우편 만료 기본 기간
- 서버/운영 우편(2·3차) 도입 여부·서버 시간 확보 방식
- 구매 상품 배송 방식 / 쿠폰 시스템 도입 여부
- (※ 보상 지급량/상한은 **우편함 결정이 아님** — 각 보상 발행 주체가 [[재화 정책 초안]] 참고해 발행 시 결정. §5 책임 경계.)
