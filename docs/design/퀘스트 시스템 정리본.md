## 1. 목적

퀘스트는 유저가 "지금 무엇을 하면 좋은지"를 알게 만드는 목표 시스템이다. 정확한 목적은 유저에게 지속적으로 **단기적 목표**를 부여해, 끝없이 다음 목표를 따라가며 플레이하게 만드는 것이다.

방치형 RPG는 자동 진행만으로도 굴러가지만, 목표가 없으면 플레이가 흐릿해진다. 퀘스트는 전투·강화·장비·유물·스테이지 진행을 짧은 행동 단위로 묶어, 유저가 "하나만 더" 달성하고 싶게 만드는 연속 목표 흐름을 제공한다.

퀘스트가 맡는 역할:

| 역할 | 설명 |
|---|---|
| 방향 제시 | 신규/복귀 유저가 다음 행동을 잃지 않게 함 |
| 단기 목표 연쇄 | 작은 목표를 계속 제시해 끝없이 따라갈 수 있는 진행감 제공 |
| 시스템 온보딩 | 강화·장비·유물·보스 등 성장축을 자연스럽게 노출 |
| 보상 루프 | 플레이 행동을 수령식 보상으로 마무리 |

## 2. 기본 원칙

1. **퀘스트는 별도 시스템이다.**
   - 리텐션은 출석·복귀·재방문 구조를 다룬다.
   - 퀘스트는 목표/진행도/완료/수령을 다룬다.
   - 일일 퀘스트는 두 시스템의 접점이지만, 소유권은 퀘스트 시스템에 둔다.

2. **운 기반 목표는 기본 퀘스트에 넣지 않는다.**
   - 잭팟 N회, 특정 고족보 N회, 특정 등급 장비/유물 획득 같은 목표는 운이 안 따르면 달성 불가가 된다.
   - 이런 목표는 업적이나 이벤트 도전으로만 검토한다.

3. **퀘스트는 행동량으로 달성 가능해야 한다.**
   - 처치, 강화, 골드 획득, 스테이지 도달, 보스 처치처럼 누적 행동으로 확실히 전진하는 목표를 우선한다.

4. **보상은 수령식이다.**
   - 조건 충족 시 바로 지급하지 않는다.
   - 유저가 퀘스트 패널에서 `받기`를 눌러 보상을 수령한다.
   - 수령 직후 `flush()`한다.

5. **수치는 지금 확정하지 않는다.**
   - 목표 횟수, 보상 배수, 완료 보너스는 밸런스 단계에서 조정한다.

## 3. 퀘스트 카테고리

퀘스트는 카테고리를 나눠 확장한다.

| 카테고리 | 주기 | 목적 | 1차 여부 |
|---|---|---|---|
| 메인 퀘스트 | 1회성/순차 | 온보딩, 장기 진행 가이드 | 1차 |
| 일일 퀘스트 | 일일 리셋 | 매일 할 일 제시 | 1차 |
| 반복 퀘스트 | 반복 가능 | 계속 플레이할 작은 보상 | 후보 |
| 이벤트 퀘스트 | 기간 한정 | 운영 이벤트 목표 | 후보 |
| 업적형 도전 | 영구 | 특수 달성 목표 | 업적 시스템과 경계 필요 |

### 3-1. 메인 퀘스트

메인 퀘스트는 튜토리얼 이후의 느슨한 가이드다.

1차 작업에 포함한다. 튜토리얼이 "긁기와 강화"를 짧게 체험시키는 역할이라면, 메인 퀘스트는 그 이후에 장비·보스·유물 같은 다음 성장축을 순차적으로 보여주는 역할을 맡는다.

후보:
- 강화 1회 하기
- 장비 소환 1회 하기
- 장비 장착하기
- 보스 10 클리어하기
- 유물 획득/장착하기

주의:
- 튜토리얼처럼 입력을 강제하지 않는다.
- 이미 완료한 행동은 모두 소급 완료될 수 있어야 한다.
- 성장축 해금/노출과 연결될 가능성이 높다.

### 3-2. 일일 퀘스트

일일 퀘스트는 매일 갱신되는 짧은 목표다.

현재 카탈로그는 고정 7종이다(처치 3 + 강화 + 보스 + 골드 + 소환 — `data/src/quests_daily.yaml`).

그중 **실제 노출은 6종**이다. `소환` 타입은 개발은 해두되 `exposed=false`로 비활성화(비노출)하고, 다이아·가루 공급량이 안정된 뒤 노출한다.

| 타입 | 예시 | 비고 |
|---|---|---|
| 처치 | 적 N마리 처치 | 자동 진행으로도 달성 가능 |
| 강화 | 강화 N회 구매 | 골드 소비와 연결 |
| 보스 | 보스 K회 처치 | 성장 게이트 확인 |
| 획득 | 골드 N 획득 | 플레이량 기반 |
| 소환 | 장비/유물 소환 N회 | 개발은 해두되 1차 노출은 비활성. 다이아·가루 공급량이 안정된 뒤 활성화 |

제외:
- 잭팟 N회
- 특정 족보 N회
- 특정 등급 장비/유물 뽑기
- 광고 시청 필수 목표

광고는 보너스 선택지로 둘 수 있지만, 일일 완료 조건에 강제로 넣지 않는다.

### 3-3. 반복 퀘스트

반복 퀘스트는 계속 플레이하는 유저에게 작은 보상을 주는 구조다.

예시:
- 적 100마리 처치마다 보상
- 강화 20회마다 보상
- 보스 5회 처치마다 보상

반복 퀘스트는 보상을 너무 자주 주면 경제를 흔들 수 있으므로 1차에서는 제외한다.

### 3-4. 이벤트 퀘스트

이벤트 퀘스트는 운영 기간 동안만 활성화되는 목표다.

예시:
- 이벤트 기간 중 보스 K회 처치
- 이벤트 기간 중 골드 N 획득
- 이벤트 기간 중 장비 소환 N회

보상 지급량과 재화 구성은 이벤트 발행 주체가 정한다. 퀘스트 시스템은 목표 판정과 수령 메커니즘만 담당한다.

## 4. 진행도 계산

기본은 누적 stat의 델타로 계산한다.

```
progress = BackendService.get_stat(stat_key) - base_stats[stat_key]
```

일일 퀘스트는 날짜가 바뀔 때 현재 누적 stat을 기준값으로 저장한다.

저장 후보:

```
quests_daily_date: "2026-06-11"
quests_daily_ids: ["daily_kill_1", "daily_upgrade_1", "daily_boss_1"]
quests_daily_base: { total_kills: 120, upgrades_bought: 34, boss_kills: 3 }
quests_daily_claimed: { daily_kill_1: true }
```

메인/반복/이벤트 퀘스트는 카테고리별 namespace를 둔다.

필요 stat 후보:

| stat | 설명 |
|---|---|
| `total_kills` | 누적 적 처치 |
| `upgrades_bought` | 강화 구매 횟수 (**전체** — 강화 종류 무관) |
| `upgrades_bought_<track>` | **트랙별** 강화 구매 횟수 ("공격력 강화 N회" 등 — 아래 §4-1) |
| `gold_earned` | 누적 골드 획득 |
| `boss_kills` | 보스 처치 |
| `stage_reached` | 최고 도달 스테이지 (✅ 구현 — `BackendService.set_stage`가 monotonic max로 갱신, 사망/블록복귀로 현재 stage 내려가도 안 줄음). "스테이지 N 도달" 퀘스트용 |
| `equipment_pulls` | 장비 소환 횟수 (메인 퀘 `main_equip_pull_1`) |
| `relic_pulls` | 유물 소환 횟수 (`shop_panel` 유물 소환 훅 — 현재 이 stat을 쓰는 메인 퀘는 없음: 유물 소환 메인 퀘는 보류·제거됨. stat·소환 기능은 유지) |
| `summon_pulls` | 장비+유물 통합 소환 횟수 (일일 `daily_summon`, Codex #15 P2) |

운 기반 stat(`jackpots` 등)은 기본 일일 퀘스트에서 제외한다.

### 4-1. 트랙별 강화 stat — 2가지 형식

강화 종류별 퀘스트는 **두 가지 형식**을 쓸 수 있다:
- **(A) "N회 강화"** = `upgrades_bought_<track>` — 그 트랙을 **산 횟수(누적)**.
- **(B) "N단계까지 완료"** = `level_<track>` — 그 트랙의 **현재 레벨(도달)**.

> 신규 세이브에선 구매 1회 = 레벨 +1 이라 A·B 가 수치상 같다. **차이는 ① 기존 세이브**(A=도입 빌드부터 집계라 과거 구매 미산입, B=실제 레벨이라 다 반영) **② 향후 환생/리셋**(A=계속 누적, B=리셋된 현재 레벨). "도달" 의미가 필요하면 **B**, "이번에 N번 했다"가 필요하면 **A**.

#### (A) `upgrades_bought_<track>` — N회 강화 (구매 횟수)

강화 구매 시 **전체(`upgrades_bought`)와 트랙별(`upgrades_bought_<track>`)을 둘 다** 누적한다. 퀘스트 `stat`에 아래 키를 쓰면 그 종류만 카운트된다.

| 강화 종류 | stat 키 |
|---|---|
| 공격력 | `upgrades_bought_attack` |
| 체력 | `upgrades_bought_hp` |
| 체력 재생 | `upgrades_bought_hp_regen` |
| 복권 배율 | `upgrades_bought_card_mult` |
| 자동 긁기 속도 | `upgrades_bought_auto_speed` |
| 긁기 범위 | `upgrades_bought_brush` |
| 저장소 | `upgrades_bought_storage` |

- **stat 키 = `upgrades_bought_` + upgrades.yaml 트랙 id.** 트랙이 추가/이름변경되면 키도 따라간다(`upgrade_panel._do_buy`가 `"upgrades_bought_" + id`로 자동 누적). ⚠️ 새 트랙 추가 시 `build_data.gd` 의 stat 화이트리스트(`qstats`)에도 그 키를 더해야 변환 경고가 안 뜬다.
- 메인·일일 **둘 다 사용 가능**(일일 base 스냅샷은 `daily_stat_keys()`가 자동 포함).
- ⚠️ **소급 안 됨**: 트랙별 구매횟수 stat은 도입 빌드부터 집계 → 기존 세이브가 그 전에 산 강화는 안 잡힌다(신규 구매부터). `upgrades_bought`(전체)는 도입 전부터 누적돼 왔으므로 무관. 작성 예시는 §11 또는 데이터 시트(`data/src/quests_*.yaml`) 참고.

#### (B) `level_<track>` — N단계까지 완료 (현재 레벨)

그 트랙의 **현재 레벨**을 본다("공격력 10단계 달성" 등). 별도 누적이 아니라 **`BackendService.get_stat("level_<track>")`이 실제 레벨(`Upgrades.get_level`)을 파생 stat으로 돌려준다** — 저장 키 추가 없음(getter가 즉석 계산). stat 키 = `level_` + 트랙 id:

| 강화 종류 | stat 키 |
|---|---|
| 공격력 | `level_attack` |
| 체력 | `level_hp` |
| 체력 재생 | `level_hp_regen` |
| 복권 배율 | `level_card_mult` |
| (자동긁기속도/긁기범위/저장소도 `level_auto_speed`·`level_brush`·`level_storage`로 가능) | |

- **실제 레벨이라 소급 O**(기존 세이브의 과거 강화도 다 반영) + **환생/리셋 시 현재 레벨 반영**. "도달" 퀘스트의 정확한 형식.
- 메인 권장(절대 달성 = `level >= target`). 일일도 가능(그날 base 대비 레벨 상승분 = `daily_delta`).
- 구현: `backend_service.get_stat`/`get_stats`가 `level_` 접두사를 `Upgrades.get_level`로 해석(파생 stat). `build_data` qstats 화이트리스트에 `level_<track>` 포함.

#### 현재 메인 퀘스트 예시 (`quests_main.yaml`, 둘 다 수록)

자동긁기속도/긁기범위/저장소는 퀘스트로 안 씀(사용자 결정) → 아래 4종(공격력/체력/체력재생/복권배율)만.

| 형식 | 퀘스트(desc) | stat | target |
|---|---|---|---|
| A 횟수 | 공격력 강화 3회 / 체력 3회 / 체력재생 2회 / 복권배율 3회 | `upgrades_bought_<track>` | 3·3·2·3 |
| B 레벨 | 공격력 5단계 / 체력 5단계 / 체력재생 3단계 / 복권배율 5단계 | `level_<track>` | 5·5·3·5 |

- **target = 받고 나서 ~30초~1분 내 달성하도록 작게**(메인은 순차 노출 = 빠른 드립). 2026-06-15 메인 전체 일괄 하향(적 처치 30→3, 300→20, 강화 30→8 등).
- ⚠️ **보스·소환·스테이지 퀘스트는 숫자가 아니라 진행도·재화에 게이트**(보스=스테이지 도달, 소환=다이아, 스테이지=도달 시간) → 최소 숫자여도 ~30초-1분보다 오래. **현재 메인 시퀀스 배치(총 25개, 2026-06-16 갱신)**: **① 빠른 비게이트(12개: 처치/강화/트랙별 횟수·레벨) → ② 소환(1개: `main_equip_pull_1` 장비 소환만 — 유물 소환 메인 퀘는 보류·제거) → ③ 스테이지 도달(10개: `main_stage_10`~`main_stage_100`, stat=`stage_reached`, target 5/10/15/20/25/30/35/40/50/60 = 10스테이지 단위 사다리) → ④ 보스(2개: `main_boss_1`/`main_boss_2`, 맨 뒤)**. ③④는 순차상 늦게 뜰 땐 이미 달성(소급)돼 즉시 수령될 수 있음(아이들 자동진행 특성 — 후반 캐치업 보상). 소환의 다이아는 우편(테스트 메일) 또는 보스 가루로 충당.
- B(레벨)는 A(횟수)보다 약간 높은 단계. 수치 전부 잠정·밸런스 보류. 순서·target은 yaml에서 조정.

## 5. 날짜 / 리셋

일일 퀘스트는 날짜 단위로 리셋한다.

- 날짜 키는 `YYYY-MM-DD`.
- 1차는 `DayUtil.today()` 로컬 시간 폴백을 사용한다.
- 서버 시간 확보 전까지 로컬 시계 조작 가능성은 감수한다.
- 앱 실행 중 날짜가 바뀌면 오늘의 일일 퀘스트를 갱신한다.

`DayUtil`은 리텐션 출석과 공유할 수 있다.

## 6. 보상 정책

퀘스트 보상은 기본적으로 **다이아**를 주력으로 본다.

골드는 스테이지와 성장 상태에 따라 가치가 크게 달라지는 진행 재화다. 고정값으로 주면 후반에 무의미하고, 스테이지 스케일로 주면 퀘스트 보상이 전투/방치 경제와 강하게 엮인다. 따라서 퀘스트의 기본 보상으로는 다소 다루기 어렵다.

원칙:
- **기본 보상 = 다이아.** 장비 소환과 연결되는 명확한 장기 목표를 만든다.
- **보조 보상 = 유물 가루 / 유물 뽑기권.** 유물 빌드 갱신 리듬과 연결한다.
- **골드는 퀘스트 기본 보상에서 제외하거나 제한적으로만 사용한다.** 필요하면 초반 온보딩/특정 메인 퀘스트에서만 검토한다.
- 운 기반 목표와 다이아/유물 가루/유물 뽑기권 보상을 묶지 않는다.

보상 타입:

| 보상 | 역할 |
|---|---|
| 다이아 | 퀘스트 기본 보상. 장비 소환 학습과 장기 목표 |
| 유물 가루 | 유물 소환/천장/직접 구매를 향한 보조 보상 |
| 유물 뽑기권 | 유물 획득 리듬을 직접 제공하는 보상 |
| 골드 | 예외적/초반용 후보. 기본값으로 쓰지 않음 |

보상 후보:

| 퀘스트 | 기본 | 후보 |
|---|---|---|
| 메인 퀘스트 | 다이아 | 유물 가루, 유물 뽑기권, 고정 유물 |
| 일일 퀘스트 | 다이아 | 유물 가루, 유물 뽑기권 조각/소량 |
| 반복 퀘스트 | 다이아 소량 또는 없음 | 유물 가루 소량 |
| 이벤트 퀘스트 | 발행 주체 결정 | 다이아, 유물 가루, 유물 뽑기권 |

## 8. 데이터 / 코드 위치

| 영역 | 위치 |
|---|---|
| 퀘스트 카탈로그 | **메인/일일 시트 분리** — `data/src/quests_main.yaml`→`data/quests_main.json`, `data/src/quests_daily.yaml`→`data/quests_daily.json` (변환 `tools/build_data.gd`) ✅ |
| 퀘스트 로직 | `scripts/quests.gd` (class_name Quests) — 카탈로그 로드(`GameData.table("quests_main")`·`GameData.table("quests_daily")`) + 순수 판정 |
| 일일 퀘스트 | `quests.gd` 내부 카테고리(별도 파일 미신설 — main/daily 한 파일) |
| 시간 헬퍼 | `scripts/day_util.gd` (`DayUtil.today()`, 퀘스트 일일 리셋·우편함과 공용) ✅ |
| 패널 UI | `scripts/quest_panel.gd` (일일 패널) + `scripts/quest_tracker.gd` (메인 HUD 트래커) ✅ |
| 보상 지급 | `BackendService.add_currency()` (gold/dia/dust 화이트리스트) |
| 저장 | `BackendService` dict 저장 + 수령 시 `flush()` |

카탈로그 (✅ 데이터화 완료, 메인/일일 시트 분리):
- **메인 = `data/src/quests_main.yaml`, 일일 = `data/src/quests_daily.yaml`**(주석 포함 원본) → `tools/build_data.gd` → `data/quests_main.json`·`data/quests_daily.json` → `GameData.table("quests_main")`·`GameData.table("quests_daily")` → `quests.gd._build(table)`가 빌드(1회 캐시). 각 시트 구조 = `quests: { id: {…} }`. 다른 테이블(upgrades·relics 등)과 동일 파이프라인.
- **정렬 = yaml 작성 순서(파일 위→아래)**. 별도 `order` 리스트 없음 — 퀘스트를 추가/재배치하려면 `quests:` 안에서 블록 위치를 옮기면 된다. (구현: `build_data`가 `JSON.stringify(..., sort_keys=false)`로 키 알파벳 정렬을 끄고 파일 순서를 json·런타임까지 보존 → `quests.gd._build`의 `for id in cat` 맵 순회가 곧 작성 순서. **이 `sort_keys=false`는 모든 data/*.json 에 적용**되어 json 이 yaml 과 같은 순서로 읽힌다.)
- **파서 제약**: 서브셋 파서가 dict 리스트(`- {…}`)를 미지원 → `rewards`는 **통화키 맵**(`rewards: { dia: 50, dust: 100 }`)으로 저장하고 `quests.gd._rewards_to_array`가 `[{currency, amount}]`로 복원.
- **검증 게이트**(`build_data.gd` `"quests_main", "quests_daily"` 케이스): 필수 필드·`target>0`·보상 통화 화이트리스트·금액>0 + `stat`/`exposed` 화이트리스트·타입으로 오타(진행도 영영 0, 숨김 깨짐) 차단.

## 9. 저장 정책

퀘스트 보상 수령은 이산 이벤트다.

수령 시퀀스:

```
보상 메모리 반영 → quest_claimed 갱신 → flush() 1회 → Events.currency_changed.emit() → 보상 토스트
```

원칙:
- 보상과 claimed를 메모리에 먼저 반영한다.
- 수령 버튼 1회마다 flush 1회.
- 모두 받기 기능을 넣는다면 메모리 일괄 반영 후 flush 1회.
- 신규 저장 컨테이너는 `_migrate`에 등록한다.

## 10. 리텐션과의 관계

일일 퀘스트는 리텐션 효과를 만든다. 하지만 시스템 소유권은 퀘스트에 둔다.

정리:
- 리텐션 문서: 왜 매일 돌아오게 할지, 출석/복귀 보상, red dot 흐름
- 퀘스트 문서: 목표 종류, 진행도, 완료/수령, 퀘스트 UI
- 재화 정책 문서: 퀘스트 보상의 재화 경계

즉, 일일 퀘스트는 리텐션에 기여하지만 리텐션의 하위 구현이 아니다.
