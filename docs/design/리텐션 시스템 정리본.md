# 리텐션 시스템 정리본

> ⚠️ **기획 초안.** 이 문서는 유저가 매일 다시 접속하고, 이탈 후 돌아왔을 때 다시 플레이를 이어가게 만드는 구조를 다룬다. 정확한 지급량·배수·복귀 기준은 아직 확정하지 않는다.
>
> 상위: [[게임 컨셉 정리본]], [[재화 정책 초안]], [[오프라인·방치 시스템 정리본]], [[백엔드 시스템 정리본]], [[UI 시스템 정리본]]. 목표/진행도 기반 시스템은 [[퀘스트 시스템 정리본]].

## 1. 목적

리텐션 시스템의 목적은 보상을 많이 뿌리는 것이 아니라, 유저가 접속했을 때 **지금 받을 것 / 돌아왔을 때 이어갈 이유**를 명확히 보여주는 것이다.

방치형 코어는 장기 성장을 만든다. 리텐션은 그 위에 짧은 방문 이유를 얹는다.

리텐션의 1차 축:

| 축 | 역할 | 주기 |
|---|---|---|
| 출석 | 접속 자체에 대한 보상 | 일일 |
| 복귀 보상 | 이탈 후 재접속한 유저의 재진입 완충 | 조건부 |
| 업적 보상 알림 | 장기 목표 달성 후 미수령 보상 환기 | 영구 |
| 퀘스트 연계 | 오늘 할 일을 보여주는 별도 시스템과 연결 | 일일/상시 |

## 2. 기본 원칙

1. **수령식으로 통일한다.**
   - 조건 충족과 보상 지급을 분리한다.
   - 유저가 패널에서 `받기`를 눌렀을 때 재화가 들어온다.
   - 받을 것이 있으면 진입 버튼에 red dot을 표시한다.

2. **리텐션은 우편함과 독립한다.**
   - 출석·복귀 보상은 리텐션 패널에서 직접 수령한다.
   - [[우편함 시스템 정리본]]은 테스트/운영/이벤트 일회성 보상 전달 통로다.
   - 두 시스템은 claim, red dot, flush 패턴을 공유할 수 있지만 1차 책임은 분리한다.

3. **퀘스트는 별도 시스템으로 둔다.**
   - 목표/진행도/완료/수령은 [[퀘스트 시스템 정리본]]이 소유한다.
   - 일일 퀘스트는 리텐션 효과를 만들지만, 리텐션 문서의 하위 구현이 아니다.
   - 리텐션은 퀘스트의 red dot이나 미수령 상태를 상위 알림에 포함할 수만 있다.

4. **보상은 성격별로 나눈다.**
   - 출석/복귀 보상은 접속 유인이므로 골드 또는 소량 다이아 후보로 본다.
   - 퀘스트 보상은 [[퀘스트 시스템 정리본]] 기준에 따라 다이아를 기본값으로 본다.
   - 유물 가루/유물 뽑기권은 유물 빌드 갱신 리듬과 연결되는 보상으로 별도 검토한다.
   - 재화별 역할과 무료 지급 경계는 [[재화 정책 초안]]을 따른다.

5. **수치는 밸런스 단계에서 정한다.**
   - 이 문서는 구조와 책임 경계를 정한다.
   - 지급량, 배수, 복귀 기준은 [[밸런스 초안]]과 플레이 로그를 보고 조정한다.

## 3. 날짜 / 시간 기준

### 3-1. 날짜 경계

리텐션의 기본 날짜 단위는 `YYYY-MM-DD`다.

- 출석은 오늘 수령했는지로 판정한다.
- 복귀 보상은 마지막 접속 시각과 현재 시각 차이로 후보를 판단한다.
- 앱 실행 중 자정을 넘길 수 있으므로, 현재 날짜와 마지막 판정 날짜를 비교해 갱신한다.

### 3-2. 시간 소스

1차 구현은 로컬 시간을 폴백으로 쓴다.

단, 시간 호출은 반드시 한 지점으로 모은다.

```
DayUtil.today()   # "YYYY-MM-DD" 로컬 날짜 (구현됨 — 퀘스트 일일 리셋과 공용)
```

> 현재 `scripts/day_util.gd`는 일일 퀘스트용으로 이미 구현되어 있고 `today()`만 제공한다. 복귀 보상에 unix 초가 필요해지면 `now_unix()` 같은 헬퍼를 같은 파일에 추가해 호출부를 한 지점으로 유지한다.

이유:
- kplay SDK에 별도 서버 시간 API가 없으면 로컬 시간 조작을 완전히 막기 어렵다.
- 지금은 랭킹이 비활성이고 리텐션 보상도 핵심 경쟁 재화가 아니므로 1차는 감수 가능하다.
- 추후 자체 백엔드나 신뢰 가능한 시간 소스를 붙일 때 호출부를 바꾸지 않기 위해 추상화한다.

우편함은 1차에서 `Mailbox.now()`(`scripts/mailbox.gd`, unix 초 로컬 폴백)를 쓴다. 나중에 `DayUtil`이 안정되면 시간 소스를 통합한다.

## 4. 출석

출석은 "오늘 접속했다"는 가장 낮은 허들의 보상이다.

### 4-1. 구조

출석은 트랙 구조로 둔다.

| 트랙 | 설명 |
|---|---|
| 상시 출석 | 항상 열려 있는 기본 7일 순환 |
| 기간 출석 | 이벤트 기간에만 열리는 별도 트랙 |
| 복귀 출석 | 일정 기간 미접속 후 돌아온 유저에게 열리는 별도 트랙 |

각 트랙은 독립 상태를 가진다.

저장 후보:

```
daily_tracks: {
  base: { last_claim_date, streak, cycle_index },
  event_xxx: { last_claim_date, streak, cycle_index },
  comeback_xxx: { started_at, last_claim_date, day_index }
}
```

1차는 상시 출석만 구현해도 된다. 다만 저장 구조와 UI는 트랙 확장을 막지 않게 둔다.

### 4-2. 상시 출석

- 7일 순환을 기본으로 본다.
- 오늘 수령하지 않았으면 받을 수 있다.
- 하루를 놓치면 연속일을 리셋할지, 단순 다음 칸으로 유지할지는 미정이다.
- 7일차는 더 큰 보상을 줄 수 있지만, 배수는 확정하지 않는다.

### 4-3. 기간 출석

기간 출석은 이벤트 운영이 필요해졌을 때 추가한다.

- `start_date`, `end_date` 범위 안에서만 노출한다.
- 기간이 끝난 트랙은 숨긴다.
- 보상 지급량은 리텐션 문서가 아니라 이벤트 발행 주체가 정한다.

## 5. 업적 보상 알림

업적은 장기 목표다.

기존 `scripts/achievements.gd`와 `data/src/achievements.yaml` 기반을 유지하되, 보상 수령 상태를 추가한다.

상태:

| 상태 | 의미 |
|---|---|
| locked | 아직 조건 미달성 |
| unlocked | 조건 달성, 보상 미수령 |
| claimed | 보상 수령 완료 |

저장 후보:

```
achievements: { id: true }   # 기존 해금 상태
ach_claimed: { id: true }    # 신규 수령 상태
```

원칙:
- 업적 해금 알림은 지금처럼 토스트로 보여줄 수 있다.
- 보상은 자동 지급하지 않고 업적/보상 패널에서 수령한다.
- 업적 시스템 자체는 별도 모듈로 유지하고, 리텐션은 미수령 상태를 red dot에 반영한다.

보상 후보:
- 대부분 골드
- 초반 주요 업적 일부에 소량 다이아/유물 가루 가능
- 유물 온보딩과 연결되는 최초 보상은 별도 검토

## 6. 복귀 보상

복귀 보상은 오프라인 정산과 다르다.

| 항목 | 오프라인 정산 | 복귀 보상 |
|---|---|---|
| 기준 | 떠나 있던 시간 동안 쌓인 골드 | 일정 기간 이탈 후 돌아온 유저 |
| 목적 | 방치 수입 지급 | 재진입 마찰 완화 |
| 지급 | 접속 시 정산 | 리텐션 패널에서 수령 |
| 상한 | 저장소 상한 | 별도 정책 |

1차에서는 복귀 보상을 바로 구현하지 않아도 된다. 다만 구조는 열어둔다.

후보:
- 3일 이상 미접속 후 복귀 출석 트랙 오픈
- 7일 이상 미접속 후 3일짜리 복귀 트랙 오픈
- 복귀 첫날에 골드 + 소량 다이아 후보

주의:
- 오프라인 정산과 중복으로 과지급되지 않게 한다.
- 복귀 보상은 "돌아오면 다시 시작할 수 있음"을 돕는 장치이지, 장기 방치를 최적 전략으로 만드는 장치가 아니다.

## 7. 퀘스트 연계

퀘스트는 리텐션과 연결되지만 리텐션의 하위 시스템이 아니다.

연계 지점:
- 일일 퀘스트의 미수령 보상이 있으면 상위 red dot에 반영할 수 있다.
- 출석 패널에서 "오늘의 퀘스트 보기" 버튼으로 퀘스트 패널을 열 수 있다.
- 복귀 유저에게는 메인/일일 퀘스트를 통해 다음 행동을 제안할 수 있다.

소유권:
- 퀘스트 목표, 진행도, 완료 판정, 보상 수령 = [[퀘스트 시스템 정리본]]
- 출석, 복귀 보상, 재방문 red dot 흐름 = 리텐션

## 8. 보상 정책

리텐션 보상은 출석/복귀/업적 알림의 성격에 맞춰 정한다.

골드를 줄 경우 고정값은 후반에 무의미하므로 현재 스테이지 기준 스케일을 검토한다. 다만 퀘스트 보상처럼 목표 달성에 대한 기본 보상은 골드가 아니라 다이아 쪽이 더 적합하다.

재화 방향:

| 보상 출처 | 기본 | 후보 |
|---|---|---|
| 출석 | 골드 | 소량 다이아/가루 |
| 업적 | 골드 | 일부 최초 업적에 다이아/가루 |
| 복귀 | 골드 | 소량 다이아 |
| 이벤트 출석 | 발행 주체 결정 | 다이아/가루 가능 |

퀘스트 보상 정책은 [[퀘스트 시스템 정리본]]에서 다룬다. 리텐션은 출석·복귀·업적 알림 중심으로 본다.

리텐션은 다이아/가루/유물 뽑기권의 정식 공급처가 될 수 있지만, 1차에서는 "후보"로만 둔다. 다이아는 장비 소환, 유물 가루와 유물 뽑기권은 유물 루프와 연결되므로 무료 지급량을 쉽게 열면 안 된다.

## 9. UI / 진입

리텐션은 출석/복귀 보상 중심 패널로 시작한다.

진입:
- HUD 상단 또는 내비 보조 위치에 `미션` 또는 `보상` 버튼을 둔다.
- 받을 것이 있으면 공용 red dot을 표시한다.
- 위치는 UI 개편 가능성이 있으므로 상수 또는 export로 모은다.

패널:

| 탭 | 내용 |
|---|---|
| 출석 | 상시 출석, 기간 출석, 복귀 출석 |
| 업적 | 미수령 업적 보상 요약 또는 업적 패널 이동 |
| 퀘스트 | 별도 퀘스트 패널 이동 버튼 |

원칙:
- 패널이 열려도 게임은 멈추지 않는다.
- UI는 `panel_overlay_base`/`UIManager.register_overlay` 계열과 맞춘다.
- red dot 표시는 공용 컴포넌트를 쓴다. 판정은 리텐션 쪽 `RetentionStatus.has_claimable()`이 소유한다.

## 10. 데이터 / 코드 위치

| 영역 | 위치 |
|---|---|
| 출석 로직 | `scripts/daily_rewards.gd` 후보 |
| 업적 로직 | `scripts/achievements.gd` 확장 |
| 통합 판정 | `scripts/retention_status.gd` 후보 |
| 시간 헬퍼 | `scripts/day_util.gd` (구현됨 — 퀘스트 일일 리셋과 공용, `today()` 제공) |
| 패널 UI | `scripts/retention_panel.gd` 후보 |
| 보상 정책 | [[재화 정책 초안]] 기준. 골드 지급 시 `scripts/balance.gd` `reward_gold(stage, mult)` 후보 |
| 저장 | `BackendService` dict 저장 + 수령 시 `flush()` |

카탈로그 방향:
- 업적은 기존 `data/src/achievements.yaml`을 확장한다.
- 출석은 1차 코드 상수로 시작 가능하다.
- 운영/이벤트가 잦아지면 `data/src/retention.yaml` 같은 데이터화로 넘긴다.
- 퀘스트 카탈로그는 [[퀘스트 시스템 정리본]]에서 별도로 다룬다.

## 11. 저장 정책

리텐션 보상 수령은 이산 이벤트다.

수령 시퀀스:

```
보상 메모리 반영 → claimed/last_claim 갱신 → flush() 1회 → Events.currency_changed.emit() → NotificationManager.reward(보상 토스트)
```

> 우편함·퀘스트 수령 시퀀스(`mailbox_panel.gd`/`quest_panel.gd`)와 동일 패턴이다. 토스트는 `NotificationManager.reward()` 단일 경로를 쓴다.

원칙:
- 수령 버튼 1회마다 flush 1회.
- 모두 받기 기능을 넣는다면 보상과 claimed를 메모리에 모두 반영한 뒤 flush 1회.
- 재화 변경 후 HUD 갱신 이벤트를 보낸다.
- `_migrate`에 신규 저장 컨테이너 기본값을 등록한다.

## 12. 1차 구현 범위

권장 1차:
- `DayUtil` 로컬 시간 폴백
- 상시 출석 7일 트랙
- 업적 보상 수령 상태(`ach_claimed`)
- 리텐션 패널
- 공용 red dot 연동
- 수령 후 `flush()` + 재화 HUD 갱신 + 보상 토스트

1차 제외:
- 서버 시간 확보
- 기간 이벤트 출석
- 복귀 출석
- 정시 보상
- 광고 2배 보상
- 푸시 알림
- 우편함과 보상 통합
- 퀘스트 시스템 본체

## 14. 최소 검증 질문

리텐션 항목을 추가할 때 아래를 확인한다.

1. 이 보상은 유저에게 오늘 다시 접속할 이유를 주는가?
2. 수령 직후 무엇을 하면 되는지 명확한가?
3. 목표/진행도 시스템이라면 퀘스트 문서에서 다루는 것이 맞지 않은가?
4. 우편함이 아니라 리텐션 패널에서 처리하는 이유가 명확한가?
5. 다이아/가루/유물 뽑기권 지급이 장비·유물 경제를 흔들지 않는가?
6. 서버 시간이 없어도 1차 운영이 가능한가?
7. 저장 한도와 flush 정책을 지키는가?
